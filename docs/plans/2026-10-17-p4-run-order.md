## 20261017_41_notes_visibility_case_team.sql (owner ١٦٩)

**What it does:**
- Adds `public.case_team_members` and the SQL definition of a case team (`public.case_team_user_ids`): the lead, the filer and the added members, each only while an active member of the case's firm. The client is never on the team.
- Adds `case_team` as a third scope on `case_notes`.
- Pins each note's scope in RLS on `case_notes`, `lawyer_client_notes` and `consultation_notes`.
- Drops the platform-admin read of private notes.
- Revokes every guest privilege on the four tables and on the seven new functions.

**Prerequisites:** 20260903_phase2, 20260905_phase3 and 20260910_case_notes, all live already. The file raises if any is missing.

**Order relative to the code:** either order works.
- **Code before SQL:** `GET /api/v1/cases/[id]/team` answers 503, the case page greys out «فريق القضية» with the reason, and private and firm notes behave as today.
- **SQL before code:** the old code never sends `case_team`. Its client-notes POST may still stamp `firm_id` on a private note, and the new rule accepts that.
- **Recommended:** SQL first, then deploy.

**Docker proof:**

```bash
M=supabase/migrations; R=supabase/tests/rls; bash $R/run.sh \
  $M/20260903_phase2_clients_and_firm_membership.sql $M/20260904_phase5_deadline_radar.sql \
  $M/20260905_phase3_consultations_and_contracts.sql $M/20260910_case_notes.sql \
  $M/20261017_41_notes_visibility_case_team.sql $M/20261017_41_notes_visibility_case_team.sql \
  $R/notes_visibility_case_team.test.sql
```

- The file is applied twice, and T0–T18 all pass.
- **Negative controls:**
  - Without the two 20261017_41 lines, T0 fails (`case_team_members does not exist`).
  - With the active-member filter removed from `case_team_user_ids`, T10 fails, because the client who filed the case is counted on its team.
- The older `case_notes.test.sql` still passes with 20261017_41 applied. Its T5 now accepts the 42501 the scope rule raises before the CHECK.

**Behaviour change to tell the owner:**
- A private note is now readable by its author only. The platform admin can no longer read private case or client notes.
- The firm owner does not see «فريق القضية» notes unless they are on the team.

**Post-run check:** the `_verify.sql` section "20261017_41 applied (case-team note scope)" must say `t`, followed by the `OK` NOTICE.

## 20261017_44_test_accounts_never_listed.sql (owner ١١٥)

**What it does:**
- Adds `public.test_accounts`: service-role only, with RLS on, no policy, and no privilege for anon or authenticated.
- Backfills the exact e-mails that `seed-test-lawyers.mjs` and `seed-clean-test-accounts.mjs` create, plus every `…@nzamy.test` account. Matching is by exact address, not the `@nezamy.sa` domain, because staff use that domain too.
- Adds a trigger on `lawyer_profiles` and `provider_profiles` that keeps `marketplace_visible = false` for a registered account, and un-lists those accounts once.

**Why:** the ten seeded test lawyers are `verified + marketplace_visible`. Every public lawyer surface keys on those two columns:
- `/api/v1/lawyers` and `/api/v1/lawyers/[id]`;
- `/lawyers/[slug]`;
- the community «أكثر المجيبين» list and the answer badges;
- public reviews;
- anon REST.

**Prerequisites:** none beyond the live schema. The file skips a table that lacks `(user_id, marketplace_visible)`.

**Order relative to the code:** either order works.
- The seed scripts on this branch register their accounts in `test_accounts` and stop setting `marketplace_visible = true`.
- If you run a seed script before the migration, it reports «Not registered as a test account (run 20261017_44 first)».
- **Recommended:** run the SQL first, then any seed script.
- **Do not run the seed scripts as part of this batch.** They write production through `.env.local`.

**Docker proof:**

```bash
M=supabase/migrations; R=supabase/tests/rls; bash $R/run.sh \
  $R/prelude_provider_profiles_live.sql $R/prelude_test_accounts_emails.sql \
  $M/20261017_44_test_accounts_never_listed.sql $M/20261017_44_test_accounts_never_listed.sql \
  $R/test_accounts_never_listed.test.sql
```

- The file is applied twice, and T1–T7 pass.
- **Negative controls:**
  - Without the migration, T1 fails.
  - With the trigger removed (and the file's own verify relaxed), T4 fails: a test lawyer re-lists themselves.

**Post-run check:** the `_verify.sql` section "20261017_44 applied (test accounts never listed)" must say `t`, with the NOTICE «N registered test account(s), none marketplace-visible».

**After the run:**
- **New test accounts:** register them through the seed scripts, or with `insert into public.test_accounts (user_id, source) values ('<uuid>', 'manual');` in the SQL editor. The listing is removed on the account's next profile write.
- **Not covered by this file:** community posts and answers written by test accounts stay public. Moderate them from the admin console (`/dashboard/admin/community`) or delete them.

## Code-only changes for ١١٥ (no SQL)

**Deploy order:** none. Each change is safe on its own.

- **`workflowStore.ts`** (the browser store): it reads and writes only in demo mode.
  - **`/services` wizard:** it now posts a real request to the نظامي team queue (`receiver: ai_workspace`, payment 0 / not_required), and sending requires sign-in. Before, it «saved» into the visitor's browser and showed success.
  - **Four AI pages** (contract-drafter, micro, ngo/volunteer-contract, gov/judgment-drafter): they show «تم الحفظ برقم» in demo mode only.
  - **Firm overview:** the fixture KPIs, «البنود العاجلة» and «آخر النشاطات» appear in demo mode only. Production shows an honest note instead.
  - **Provider requests page:** in production it shows `DashboardComingSoon` (no server feed exists). Its two nav entries are badged «قريباً».
- **Library demo content** (`demo-data-access.ts`, smart-folder seed, `/laws/feqh-preview` demo book, `/book/rawd-al-murbi` fallback): shown in demo mode, or in a non-production build with `NEXT_PUBLIC_LIB_DEMO_FALLBACK=1`. A production build can no longer turn it on.
- **Smart folders:** a signed-in user no longer falls back to the guest's browser folders when the API fails.
- **Sessions** (`useUser.ts`):
  - entering demo signs out any real Supabase session in this browser (`scope: "local"`), and so does demo logout;
  - a real session clears the demo markers (`nzamy_demo_role`, `nzamy_demo_key`, and the cookie) at start and at logout.
- **`apiMutate`:** it refuses every write in demo mode, so demo data cannot reach any database.
- **Community demo:** a seed question can now be answered. Its copy is stored locally with the answer, and the feed de-duplicates it.
