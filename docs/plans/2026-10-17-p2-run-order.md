## Precondition for 20261017_20: does the server's PostgREST apply a function's time limit?

The 4-second limit is stored on the function. Postgres only honours it when PostgREST applies it **before** the call, which PostgREST v12 and later do (the setting `db-hoisted-tx-settings`, which includes `statement_timeout` by default). A plain `select library.search_principles_page(...)` in the SQL Editor is **not** limited. That is Postgres behaviour, proven in Docker; see the test header.

Check once on the server, in the folder that holds the self-hosted Supabase `docker-compose.yml`:

```bash
docker compose images rest
```

- The tag must be **v12.0.0 or later** (for example `postgrest/postgrest:v12.2.12`).
- Then run `grep -n HOISTED docker-compose.yml .env`. If `PGRST_DB_HOISTED_TX_SETTINGS` is set, it must still list `statement_timeout`. Not set at all is fine: the default includes it.

On an older PostgREST nothing breaks. The function runs exactly as the inline query does today, still with no limit. Tell the developer in that case.

## Step 1b (optional): search statistics

2. `20261017_21_library_fts_statistics.sql`. It ends with `NOTICE: 20261017_21 OK — statistics target 1000 and fresh word statistics on every library fts column present`.

**What it fixes:** Postgres estimates any word outside its list of common words at about **933 matching articles**. The real count for a rare word is 0–46. With a category or law-type filter, that estimate makes the laws search walk the whole articles table instead of using the search index, and a cold search on a rare word takes seconds. The file lists 10 times more words, so a rare word is estimated at a few dozen rows. In Docker, a one-row word dropped from 40 estimated rows to 4.

**What it costs:** ANALYZE reads each of the three tables once. Searches keep working while it runs. On `articles` it can take up to a minute.

- If the SQL Editor times out, the whole file rolls back and nothing changes. Then run, one table at a time:
  `alter table library.articles alter column fts set statistics 1000; analyze library.articles (fts);`
  and the same for `library.feqh_blocks` and `library.principles`.
- **Optional check (before and after):**
  `explain select id from library.articles where fts @@ to_tsquery('simple', '''شفعة'' | ''الشفعة''');`
  The `rows=` of the top line drops from about 933.
- **When to re-run:** after any migration that drops and re-creates an `fts` column, which resets the setting. A library reload keeps it.

The new `2026-10-17 — 20261017_20` section, prints `_verify: 20261017_20 OK`. Before the migration it prints a NOTICE that it is not applied yet, and it does not stop the deploy.
