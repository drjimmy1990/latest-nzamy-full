## Step 1 (before the deploy): `20261017_30_business_delegations.sql`

Paste the whole file and click Run. It ends with:
`NOTICE: 20261017_30 verify: OK — business_delegations register (owner grants/revokes, members read, no delete), delegate UPDATE arm on business_profiles, metadata.features pinned for non-admin sessions`.

**What changes for whom:**
- **The company owner:** nothing changes for their own edits. They can now register an active team member as a delegate (optionally until a last day) and revoke a delegation, on «التفويض».
- **A registered delegate:** can edit the company data on «بيانات المنشأة» (the same columns as the owner). They still cannot change the verification status, the plan or the owner.
- **Any other member:** reads the company data and the register, and edits nothing. This is the WP-6 rule as before.
- **Revocation** is final and stays in the register. Suspending or removing a member ends their delegation by itself. Nobody can delete the register through the API.
- **`metadata.features`**, the four company flags the admin console writes, can no longer be overwritten by the company through REST. Server routes and admins still write them.

**Docker proof:** `supabase/tests/rls/business_delegations.test.sql`, 25 checks, with the chain written in its header.
- The migration was run twice in the chain (idempotent).
- Negative control: the same chain without the migration stops with exit 3 (`relation "public.business_delegations" does not exist`).
- Check N1 is the state before the migration: a member with no delegation, even a `legal_manager`, updates 0 company rows.

**`_verify.sql`** has a new last section, `_verify: 20261017_30 OK …`. Before the migration runs, the section prints `… is not applied yet …` and passes. Both runs were checked in Docker.

**Check from outside (public anon key).** This must answer `401`:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "apikey: $ANON" "https://auth.nezamy.sa/rest/v1/business_delegations?select=id&limit=1"
```

**Deploy-order cliffs:**
- Code deployed **before** this file: «التفويض» answers «سجل التفويضات غير مفعّل بعد على الخادم» (503). The owner's own company edits keep working, because the routes ask about delegation only after the owner check fails.
- This file **before** the code: nothing changes for anyone until the code is live.

**Re-run cliffs:**
- **Re-running `20260921_03_entity_rls_recursion_fix.sql`** drops every policy on `business_profiles` by catalogue, the delegate policy included. Delegates lose write access, which fails closed; the owner is unaffected. `_verify.sql` then raises `the owner or the delegate UPDATE policy on business_profiles is missing`. **Re-run `20261017_30` after it.**
- Re-running `20260922_03` does not touch anything in this file. No column grant on `business_profiles` was added or widened.

**Rollback:** in the file header. Dropping the table loses the register.
