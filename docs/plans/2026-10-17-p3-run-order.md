## Step 1 (before the deploy): `20261017_30_business_delegations.sql`

Paste the whole file and click Run. It ends with:
`NOTICE: 20261017_30 verify: OK — business_delegations register (owner grants/revokes, members read, no delete), delegate UPDATE arm on business_profiles, metadata.features pinned for non-admin sessions`.

**What changes for whom:**
- **The company owner:** nothing changes for their own edits. They can now register an active team member as a delegate (optionally until a last day) and revoke a delegation, on «التفويض».
- **A registered delegate:** can edit the company data on «بيانات المنشأة» (the same columns as the owner). They still cannot change the verification status, the plan or the owner.
- **Any other member:** reads the company data and the register, and edits nothing. This is the WP-6 rule as before.
- **Revocation** is final and stays in the register. Suspending or removing a member ends their delegation by itself. Nobody can delete the register through the API.
- **`metadata.features`**, the four company flags the admin console writes, can no longer be overwritten by the company through REST. Server routes and admins still write them.

**Docker proof:** `supabase/tests/rls/business_delegations.test.sql`, 25 checks, with the chain written in its header.
- The migration was run twice in the chain (idempotent).
- Negative control: the same chain without the migration stops with exit 3 (`relation "public.business_delegations" does not exist`).
- Check N1 is the state before the migration: a member with no delegation, even a `legal_manager`, updates 0 company rows.

**`_verify.sql`** has a new last section, `_verify: 20261017_30 OK …`. Before the migration runs, the section prints `… is not applied yet …` and passes. Both runs were checked in Docker.

**Check from outside (public anon key).** This must answer `401`:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "apikey: $ANON" "https://auth.nezamy.sa/rest/v1/business_delegations?select=id&limit=1"
```

**Deploy-order cliffs:**
- Code deployed **before** this file: «التفويض» answers «سجل التفويضات غير مفعّل بعد على الخادم» (503). The owner's own company edits keep working, because the routes ask about delegation only after the owner check fails.

**Re-run cliffs:**

Delegates lose write access, which fails closed; the owner is unaffected. `_verify.sql` then raises `the owner or the delegate UPDATE policy on business_profiles is missing`. **Re-run `20261017_30` after it.**

## No SQL: owner decisions ١٥ / ١٩, the client's view of a case

Nothing to run. The client's «ملخص القضية» comes from a fixed server projection, `GET /api/v1/client/cases/[id]/summary`:
- The caller's own RLS client first reads the case row from `service_requests`. That admits the requester and the company's active members; a stranger gets 404.
- Only then does the server read `hearings` and `case_stages` for that case, naming the column lists in `src/lib/clientCaseSummary.ts`. Never selected: notes, minutes, judge, circuit, court case number, metadata, hearing titles. Only `judicial` and `client_meet` hearings are read.
- `case_notes` and `consultation_notes` are not read.

**Docker regression proof:** `supabase/tests/rls/client_case_view_no_internal_rows.test.sql`, chain in its header. It pins the live posture: a requester reads their case but 0 rows of `hearings`, `case_stages` and `case_notes`. The lawyer control reads all of them.

**If a later migration ever adds a requester SELECT policy** on those tables, that test stops. Every internal column would otherwise reach the browser through REST, because a row policy cannot hide columns.

**Gap, reported rather than invented:** the platform stores no operative text of a judgment («منطوق الحكم»). The client sees the outcome of the last decided degree (for example «صدر الحكم لصالحك جزئياً») and its date. Showing the operative text needs a new column that the lawyer fills in as client-visible text, separate from the internal notes.

## Step 2 (before the deploy): `20261017_31_firm_reviews_opt_in.sql`

Paste the whole file and click Run. It ends with:
`NOTICE: 20261017_31 verify: OK — firm reviews are public only by firm_profiles.public_reviews (default off, set through set_firm_public_reviews); lawyer reviews unchanged`.

**What it closes.** Today a guest can read every active review of a FIRM account straight through REST:
`GET /rest/v1/reviews?reviewee_id=eq.<firm id>`.
The only SELECT policy is `status = 'active'`. After this file:
- a firm's reviews and rating figures are visible to guests and other accounts only once the firm opts in;
- the reviewer, the firm itself and admins always see them;
- lawyer reviews are untouched (the permissive policy stays as it is).

**Who switches it:** the firm account itself (`firm_profiles.owner_user_id`), on «تقييمات المكتب» (`/dashboard/firm/reviews`). The column has no grant; the only writer is the `set_firm_public_reviews` RPC. A managing partner who is not the firm account cannot switch it. The role matrix belongs to the team-roles piece.

**Docker proof:** `supabase/tests/rls/firm_reviews_opt_in.test.sql`, 14 checks.
- The migration was run twice (idempotent).
- Negative control: without the migration the run stops at `G1 FAIL: a guest reads 1 review(s) of a firm that never opted in`. That is the live leak.
- Re-running `20260922_03` after 30 and 31 is green; its firm allowlist is unchanged.

**Check from outside (public anon key)** once a firm exists. This must answer `[]` while the firm has not opted in:

```bash
curl -s -H "apikey: $ANON" "https://auth.nezamy.sa/rest/v1/reviews?select=id&reviewee_id=eq.<FIRM_ACCOUNT_ID>"
```

There are 0 firm accounts on production today, so there is nothing to observe yet.

**`_verify.sql`:** a new last section, `_verify: 20261017_31 OK …`. Before the file runs, it prints a NOTICE and passes. Both runs were checked in Docker.

**Deploy-order cliffs:**
- Code before SQL: «تقييمات المكتب» shows «إعداد ظهور التقييمات غير مفعّل بعد على الخادم» (503), and `GET /api/v1/reviews?firm=` answers empty. Nothing else changes.
- SQL before code: nothing live shows firm reviews, so nobody sees a difference.

**Monopoly mode:** `BETA_MONOPOLY_MODE` still parks the public directory. No public page renders firm reviews yet; the opt-in and the API (`GET /api/v1/reviews?firm=<id>`) are ready for when it opens.
