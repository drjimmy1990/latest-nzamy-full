## Step 1 (before the deploy): `20261017_10_profiles_national_address.sql`

Paste the whole file and click Run. It ends with
`NOTICE: 20261017_10 verify: OK — profiles.national_address (optional, ≤300) is self-editable; the 20261016_02 lock is otherwise unchanged`.

It refuses to pass if `authenticated` still holds table-level UPDATE on `profiles` (20261016_02 is a prerequisite; it is live since 2026-10-16).

**Why before the deploy:** the new settings field sends `national_address`. With the code live and the column missing, an individual who fills that field gets a save error (42703). Nobody else is affected, because the settings form sends only the fields that changed.

**⚠ If `20261016_02` is ever re-run, re-run `20261017_10` right after it.** 20261016_02 revokes UPDATE on the whole table, which also removes this column grant, and its own verify still passes. `_verify.sql` (Step 3) catches it: `_verify: the profiles national address is broken — authenticated cannot UPDATE public.profiles.national_address …`.

## Step 2: deploy the code

Merge the branch with the others in this batch and deploy as usual (`deploy.sh` via nohup). No new dependency, so `npm install` is not needed for this branch.

## Step 3: `_verify.sql`

Two sections changed:
- **20261016_02 (older section, widened):** it now accepts `national_address` as a self-editable column. Without that change it would raise `authenticated can UPDATE public.profiles.national_address` as soon as Step 1 ran (proved in Docker).
- **20261017_10 (new, last section):** `_verify: 20261017_10 OK — profiles.national_address is optional (≤300), self-editable, owner- and admin-readable only`. Before Step 1 it prints `_verify: 20261017_10 is not applied yet …` and passes.

## Docker proof (`supabase/tests/rls/profiles_national_address.test.sql`)

The chain is in the test file's header. All three runs below were made on 2026-10-16:
- **Positive** (the migration run twice): N0–N4 PASS. The owner sets, reads back and clears the address. Another user's row is neither read nor written. Blanks and anything over 300 characters raise `check_violation`. Email, verification, metadata and user_type stay locked.
- **Negative control** (the same chain without 20261017_10): fails at `N0 FAIL: … does not exist`.
- **Re-run hazard** (20261016_02 again after 20261017_10): fails at `N1 FAIL: authenticated cannot UPDATE …`.
- `_verify.sql` sections 20261016_02 and 20261017_10, extracted and run after each chain: pass before Step 1 (NOTICE only), pass after it, raise after the hazard chain. The old 20261016_02 section raises after Step 1, which is why it was widened.
